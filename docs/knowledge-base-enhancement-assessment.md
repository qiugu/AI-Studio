# 知识库增强评估：Reranker / 图数据库 / GraphRAG

> **文档性质**：技术可行性 + 成本与资源评估（评估结论，非实施计划）
> **评估对象**：AI-Studio 知识库子系统（`backend/app/services/knowledge*.py`、`core/vector_db.py`、`utils/{document,embedding}.py`）
> **评估日期**：2026-09-11
> **评估方式**：静态代码审查 + 架构比对 + 成本建模（未执行运行时压测，结论已标注置信度）

---

## 1. 结论摘要

| 增强项 | 可行性 | 收益 | 增量基础设施成本 | 开发量 | 建议优先级 |
|--------|--------|------|------------------|--------|-----------|
| **Reranker** | 高（低风险） | 高，检索精度典型提升 15–35% | 本地 +1.5–2 GB 内存；或 API 零本地资源 | 3–5 人日 | **P1（优先）** |
| **图数据库** | 中高 | 中，是多跳推理与实体的前提 | Docker +4–8 GB 内存 | 10–15 人日 | P3 |
| **GraphRAG** | 中 | 高（全局性/多跳问题），但对简单事实问答收益有限 | 无新增常驻服务，但 **LLM 索引成本为一次性大头** | 10–20 人日 | P4 |

**核心判断（三条）**：

1. **Reranker 应立即实施**。当前检索为「单路向量召回 + 阈值截断」，无精排环节，是效果提升性价比最高的一环；且现有 `sentence-transformers` 依赖已就位，**零新增基础设施**。
2. **图数据库与 GraphRAG 应捆绑评估，但不必同时上**。图数据库是 GraphRAG 的存储前置条件，但二者可分离：先引入图存储与实体抽取管线，验证图谱质量后再接 GraphRAG 检索。
3. **GraphRAG 的真正成本不在服务器，而在索引期的 LLM 调用**。按中档规模（50 万 chunk）测算，单次全量索引约 **¥1,000–1,500**；大规模（500 万 chunk）约 **¥1.0–1.5 万/次**。这是决策的关键变量。

**前置阻塞项（P0，必须先修）**：静态审查发现 Agent 知识库工具与 Workflow 知识库节点存在**参数名不匹配缺陷，当前功能不可用**（详见 §2.3 与附录 A）。任何增强都建立在检索链路可用之上，建议先行修复。

## 2. 现状评估

### 2.1 当前检索链路（As-Is）

```
上传文档 → Celery 异步任务
   ├─ DocumentParser 解析（txt/md/pdf/docx，纯文本抽取）
   ├─ TextSplitter 递归字符分块（chunk_size=1024, overlap=128）
   ├─ EmbeddingClient.embed()（默认本地 BAAI/bge-base-zh-v1.5, 768 维, CPU）
   └─ Qdrant upsert（collection = kb_{kb_id}, COSINE, HNSW m=16/ef=100）

检索
   └─ query 向量化 → Qdrant.search(limit=top_k, score_threshold=0.5) → 回表取 chunk 内容 → 返回
```

### 2.2 能力矩阵

| 能力 | 现状 | 说明 |
|------|------|------|
| 文档解析 | ✅ 基础 | 仅纯文本抽取，**无 OCR、无表格/版面结构还原** |
| 分块策略 | ⚠️ 基础 | 固定字符长度递归切分，**无语义/结构感知，无标题路径元数据** |
| 向量检索 | ✅ | Qdrant 单向量，COSINE |
| 关键词/稀疏检索 | ❌ 缺失 | 无 BM25/稀疏向量，无法覆盖精确术语、编号、专有名词 |
| 混合检索融合 | ❌ 缺失 | 无 RRF/加权融合 |
| **重排序（Reranker）** | ❌ 缺失 | 无精排环节，仅靠向量相似度 + 固定阈值 |
| 向量库 | ✅ Qdrant | 独立部署，非 AGENTS.md 架构图所写的 pgvector（文档与实现不一致，见附录 A） |
| **图存储 / 实体关系** | ❌ 缺失 | 无实体、关系、社区等任何图结构化表示 |
| **GraphRAG** | ❌ 缺失 | 无实体抽取、无社区摘要、无图遍历检索 |
| 检索评估/回归 | ❌ 缺失 | 无知识库相关单元测试与召回率基线 |

### 2.3 前置缺陷（P0，阻塞项）

静态 AST 校验结果（脚本比对方法定义与全部调用点）：

```
DEF  services/knowledge.py:230  KnowledgeBaseService.search(params=[self, kb_id, query, top_k, score_threshold])
CALL services/agent.py:233           kwargs=[kb_id, query_text, top_k]      ← 不匹配
CALL services/workflow_engine.py:360 kwargs=[kb_id, query_text, top_k]      ← 不匹配
CALL api/knowledge.py:349            kwargs=[kb_id, query, top_k, score_threshold]  ← 匹配
```

**结论**：`Agent 知识库工具` 与 `Workflow 知识库节点` 调用时传入关键字 `query_text`，而服务层签名为 `query`，将抛出 `TypeError: search() got an unexpected keyword argument 'query_text'`。即**这两条路径的知识库检索当前是失效的**，仅 REST 检索接口（`/knowledge-bases/{kb_id}/search`）正常。

其余需一并修复的问题见 **附录 A**。

## 3. 增强项一：Reranker（重排序）

### 3.1 必要性论证

向量检索（Bi-Encoder）将 query 与 chunk 独立编码，靠向量距离近似语义相关度，天然存在三个问题：

- **召回数量与精度矛盾**：为保证召回率需 `top_k` 放大（如 50），但向量排序质量不足以直接截断到 5–8 条上下文。
- **阈值敏感**：当前 `score_threshold=0.5` 是硬编码魔数，对短查询易漏召回，对长查询易引入噪声。
- **多主题 chunk 稀释**：1024 字符的固定分块常混合多个语义单元，向量表达被平均化。

Reranker（Cross-Encoder）将 query 与候选拼接后整体打分，注意力可交互，**排序精度显著高于 Bi-Encoder**。业界通用范式为「向量粗召回 K=30~50 → Reranker 精排 → 取 Top-N=5~8」。

据公开基准与工程实践，对中文企业文档场景，引入 Reranker 后 **Top-5 命中率典型提升 15–35%**（该区间为经验值，实际需在自有语料上建立评测集验证）。

### 3.2 方案选型对比

| 方案 | 实现 | 新增依赖 | 本地资源 | 单次延迟增量 | 成本模型 | 适配度 |
|------|------|----------|----------|--------------|----------|--------|
| **A. 本地 CrossEncoder**（推荐） | `BAAI/bge-reranker-base`（约 1.1 GB）经 `sentence-transformers` 加载 | **零**（已装） | +1.5–2 GB 常驻内存 | 约 150–400 ms（20 候选，4 核 CPU） | 一次性下载，推理零边际成本 | ⭐⭐⭐⭐⭐ |
| A'. 本地强模型 | `BAAI/bge-reranker-v2-m3`（约 2.3 GB，568M 参数） | 零 | +3–4 GB | 约 500–1500 ms（CPU） | 同上 | ⭐⭐⭐⭐（建议配 GPU） |
| **B. 云端 Rerank API** | SiliconFlow / Cohere Rerank / Jina Reranker | 无 | 0 | 约 100–300 ms（含网络） | 按 token 或按次计费 | ⭐⭐⭐⭐（适合大流量弹性） |
| C. 多向量 / ColBERT | Qdrant 原生 multivector + MaxSim | 需换向量模型 | 存储膨胀 10–20× | 低 | **需全量重索引** | ⭐⭐（不建议现阶段） |

**推荐策略**：以 **方案 A** 为默认实现，同时将 Reranker 抽象为可插拔接口，保留 B 作为弹性/降级通道——与现有 `EmbeddingClient` 的 provider 工厂模式一致，不增加架构认知负担。

### 3.3 集成改造点

| 文件 | 改造内容 |
|------|----------|
| `backend/app/core/config.py` | 新增 `rerank_provider` / `rerank_model` / `rerank_top_k` / `rerank_candidates` |
| `backend/app/utils/rerank.py` | **新建**：`RerankerClient`（本地 CrossEncoder + API 两种 provider），进程级模型缓存 |
| `backend/app/services/knowledge.py` | `search()` 增加两段式：粗召回 `candidates` → rerank → 截断 `top_k`；返回 `rerank_score` |
| `backend/app/schemas/knowledge.py` | 检索结果 Schema 增加 `rerank_score` 字段 |
| `requirements.txt` | **无变更**（`sentence-transformers`、`torch` 已存在） |
| 前端 `KnowledgeDetail.tsx` | 检索结果展示增加 rerank 分数字段（可选） |

### 3.4 成本与资源

| 项目 | 测算 |
|------|------|
| 新增常驻服务 | 无 |
| 内存增量 | +1.5–2 GB（bge-reranker-base，CPU FP32） |
| 磁盘 | +1.1 GB（模型权重，可复用 HF 缓存卷 `hf-cache`） |
| 冷启动 | 首次加载约 3–8 s；已在 worker 内做进程级缓存，后续复用 |
| 单次查询延迟增量 | +150–400 ms（CPU） |
| 边际调用成本 | ¥0（自托管） |
| 开发工作量 | **3–5 人日**（含配置化、降级、测试） |

> **注意**：Reranker 与 Embedding 同时占用 CPU 时，Celery worker 并发（当前 `--concurrency=2`）可能放大峰值内存。建议将 Reranker 常驻于 API 进程侧（检索为同步路径）而非 worker 侧（索引为异步路径），以避免 worker 内存叠加。

## 4. 增强项二：图数据库

### 4.1 是否需要独立图库的判据

并非所有场景都需要独立图数据库。判据如下：

| 场景特征 | 是否需独立图库 |
|----------|----------------|
| 仅做「文档 → chunk → 向量」检索 | ❌ 不需要 |
| 需多跳关系查询（A→B→C），深度 ≥ 2 | ✅ 需要（或关系表 + 递归 CTE 勉强支撑） |
| 实体规模 < 10 万、跳数 ≤ 2 | ⚠️ 可用 MySQL 邻接表替代 |
| 实体规模 > 100 万、需路径/社区算法 | ✅ 需要 |

**本项目现状**：无任何实体关系建模，故图数据库并非当前阻塞项，而是 **GraphRAG 的存储前置条件**。

### 4.2 选型对比

| 方案 | 部署形态 | 内存（中小档） | 运维复杂度 | 适合规模 | 备注 |
|------|----------|----------------|------------|----------|------|
| **Neo4j Community 5.x** | 独立容器（JVM） | 2 GB heap + 2 GB pagecache ≈ **4–8 GB** | 中 | 中—大 | 生态最成熟（Cypher、APOC/GDS 图算法），**推荐** |
| **Kuzu** | 嵌入式（同进程） | 0.5–2 GB | 低 | 小—中 | 无独立服务，单文件存储，适合起步验证 |
| **Apache AGE** | PostgreSQL 扩展 | 随 PG | 低 | 小—中 | 复用关系库，但项目栈为 MySQL，**不匹配** |
| **NebulaGraph** | 分布式集群 | 每节点 8 GB+ | 高 | 大 | 学习与运维成本高，**过度设计** |
| 云图库（阿里云 GDB / 腾讯云 TGraph） | 托管 | — | 无 | 任意 | 省运维，但有数据出网与合规评估成本 |
| **MySQL 邻接表 + 递归 CTE** | 复用现有 MySQL | 0 | 最低 | 小 | **务实过渡方案**，可先在 MySQL 落实体/关系表，跑通抽取管线 |

**分阶段建议**：
- **第一阶段**：实体/关系先落 MySQL（`entities` / `relations` 两张表，含 `kb_id`、`tenant_id`），跑通 LLM 抽取与数据质量验证——**零新增基础设施**。
- **第二阶段**：当实体 > 10 万或需要多跳路径/社区检测时，迁移至 Neo4j。迁移成本主要在数据搬迁（可控），而非重写业务逻辑（前提是第一阶段的仓储层做了抽象）。

### 4.3 成本与资源

| 项目 | 小档（1k 文档） | 中档（2 万文档） | 大档（20 万文档） |
|------|----------------|------------------|-------------------|
| 预估实体数 | 3–8 万 | 30–80 万 | 300–800 万 |
| 预估关系数 | 10–30 万 | 100–300 万 | 1000–3000 万 |
| Neo4j 内存 | 2–4 GB | 4–8 GB | 32–64 GB（或分布式） |
| 磁盘占用 | < 1 GB | 1–3 GB | 10–30 GB |
| 开发工作量 | — | **10–15 人日** | 同上 + 迁移工作 |

## 5. 增强项三：GraphRAG

### 5.1 能力定位（与向量 RAG 的差异）

| 问题类型 | 向量 RAG | GraphRAG |
|----------|----------|----------|
| 「X 的定义是什么」局部事实 | ✅ 好 | ⚠️ 无优势（更贵） |
| 「X 和 Y 有什么关系」跨文档 | ⚠️ 依赖共现 | ✅ 好 |
| 「整个知识库的核心主题有哪些」全局归纳 | ❌ 差（无法覆盖全集） | ✅ 好（社区摘要） |
| 「A 通过哪些环节影响 C」多跳推理 | ❌ 差 | ✅ 好 |

**关键判断**：GraphRAG 不是向量 RAG 的替代，而是**增量能力**。对以「查条款、查定义、查参数」为主的企业文档场景，向量 RAG + Reranker 已可满足 80% 需求；GraphRAG 面向的是跨文档关联与全局归纳类问题。**若知识库以制度/规范/手册类文档为主，GraphRAG 的投入产出比需谨慎评估。**

### 5.2 两条技术路线

| 维度 | 路线 A：全量 GraphRAG（微软范式） | 路线 B：轻量增量图 RAG（LightRAG 型） |
|------|-----------------------------------|----------------------------------------|
| 索引流程 | 实体抽取 → 关系抽取 → 社区检测（Leiden）→ 社区摘要（LLM 递归） | 实体抽取 → 关系抽取 → 双层检索（低层实体/高层主题） |
| LLM 成本 | **高**（社区摘要是额外一轮大额 LLM 调用） | **中**（无社区摘要） |
| 查询延迟 | 高（需加载社区报告） | 中 |
| 全局归纳能力 | ✅ 强 | ⚠️ 中 |
| 实现复杂度 | 高 | 中 |
| 增量更新 | 差（社区变化需重算） | 好（可增量插入） |
| 推荐度 | 知识库稳定、需全局归纳 | **多数企业场景首选** |

**建议**：先做 **路线 B**（增量、成本可控），验证图谱质量与业务价值后，再评估是否补上社区摘要层。

### 5.3 索引管线设计（目标态）

```
文档 → 解析 → 分块（结构感知，携带标题路径）
   ├─[并行 1] 向量化 → Qdrant
   ├─[并行 2] LLM 实体/关系抽取 → 三元组 → 图库（实体消解/去重）
   └─[并行 3] chunk ↔ 实体 双向索引 → MySQL（支撑实体→chunk 回溯）

查询
   ├─ 向量检索（+ 关键词检索）→ RRF 融合 → Reranker → Top-N chunk
   ├─ 实体识别 → 图遍历 1-2 跳 → 关联实体/关系 → 映射回关联 chunk
   └─ 两者融合 → 上下文组装（含三元组事实）→ LLM
```

### 5.4 成本测算（核心）

#### 5.4.1 LLM 索引成本模型

单次全量索引的 token 规模：

```
抽取输入 token ≈ chunk 数 × (Prompt 模板 300 + chunk 内容 ~700)  ≈ chunk 数 × 1,000
抽取输出 token ≈ chunk 数 × 300~600（三元组 + 实体描述）
社区摘要（仅路线 A）≈ 抽取成本 × 1.2~1.4
```

按 chunk 规模的三档测算（**价格取国产经济型模型参考区间，实际以供应商报价为准**）：

| 规模 | chunk 数 | 抽取输入 | 抽取输出 | 抽取成本 | 含社区摘要（路线 A） |
|------|----------|----------|----------|----------|---------------------|
| 小档 | 2 万 | 2,000 万 token | 1,000 万 token | **≈ ¥50** | ≈ ¥70 |
| 中档 | 50 万 | 5.0 亿 token | 2.5 亿 token | **≈ ¥1,000** | ≈ ¥1,300 |
| 大档 | 500 万 | 50 亿 token | 25 亿 token | **≈ ¥10,000** | ≈ ¥13,000 |

> 计价假设：经济型模型 input ≈ ¥1/M token、output ≈ ¥2/M token。若改用中高端模型（如 GPT-4o-mini 级），成本约 **×3–5**。
> 交叉验证：微软 GraphRAG 官方经验值约为 **$2–6 / 1M token 源文档**。中档（约 5,000 万 token 源文档）换算约 $100–300 ≈ ¥720–2,160，与上表同量级，模型可信。

**关键结论**：
- 成本与**文档总量线性相关**，与内容复杂度（实体密度）相关。
- **索引是一次性成本，但重建是周期性成本**。建议：仅对新增/变更文档做增量索引（按 Δchunk 计费）；每季度至半年做一次全量重建以修正图漂移。
- 中档规模年度 LLM 成本估算：首次全量 ¥1,000 + 增量 ¥500 + 两次重建 ¥2,000 ≈ **¥3,500/年**（不含对话侧 token）。

#### 5.4.2 算力与存储

| 资源 | 说明 | 增量 |
|------|------|------|
| GPU | **非必需**。抽取走云端 LLM API；本地 reranker 用 CPU 即可 | 0（可选 +1× RTX 4090 / A10 用于本地推理加速） |
| 索引期 CPU | 抽取任务为 IO 密集（等 LLM 响应），CPU 需求低；并发放大时需限流 | +1–2 vCPU |
| 索引期内存 | Celery worker 峰值（文档解析 + 图批量写入） | +2–4 GB |
| 图存储磁盘 | 见 §4.3 | 1–30 GB |
| 队列积压 | 全量索引耗时与并发强相关（见下） | — |

**索引耗时估算**（假设 LLM 并发 8、单次抽取响应 5 s）：

| 规模 | chunk 数 | 理论耗时 |
|------|----------|----------|
| 小档 | 2 万 | ≈ 3.5 小时 |
| 中档 | 50 万 | ≈ 87 小时（约 3.6 天，建议限流错峰） |
| 大档 | 500 万 | 需分布式并发或分批处理，天数级 |

> 这意味着 GraphRAG 索引是**长时后台任务**，需要独立队列（避免阻塞现有文档处理任务）、断点续传与进度可观测能力。

### 5.5 风险与适用边界

| 风险 | 影响 | 缓解 |
|------|------|------|
| LLM 抽取质量不稳定 | 图谱噪声污染检索 | 抽取后置信度过滤 + 人工抽检；先小规模验证 |
| 多租户图谱隔离 | 跨租户数据泄漏（严重） | 图库中每个节点/边强制携带 `tenant_id`，查询强制过滤（对齐现有 `BaseRepository` 约定） |
| 成本失控 | 索引成本超预期 | 先做 1 个小知识库的端到端成本实测，再外推 |
| 增量与全量割裂 | 图数据漂移 | 设计版本化与重建流程 |
| 效果不可度量 | 无法证明投入有价值 | **前置条件：先建检索评测集**（见 §7 P0） |

## 6. 目标架构建议（To-Be）

```
┌──────────────────────────────────────────────────────────────────────┐
│ 写入侧                                                                 │
│  文档 → 解析（结构感知）→ 分块（带标题路径元数据）                        │
│    ├─[并行] 向量化 ──────────────────→ Qdrant（稠密向量）               │
│    ├─[并行] 稀疏编码 ────────────────→ Qdrant（稀疏向量，混合检索）      │
│    ├─[并行] LLM 实体/关系抽取 ────────→ 图库（MySQL → Neo4j）            │
│    └─[并行] chunk↔实体 映射 + 元数据 ─→ MySQL                          │
└──────────────────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────────────────┐
│ 读取侧                                                                 │
│  Query                                                                 │
│    ├─ 稠密检索 + 稀疏检索 → RRF 融合 → 【Reranker 精排】→ Top-N        │
│    ├─ 实体识别 → 图遍历 1–2 跳 → 关联 chunk / 三元组事实                 │
│    └─ 融合上下文 → LLM 生成（SSE 流式）                                 │
└──────────────────────────────────────────────────────────────────────┘
```

**新增组件**：`utils/rerank.py`、`utils/graph_store.py`、`services/graph_extractor.py`、Celery 独立队列（`knowledge.graph_index`），以及图库容器（可选 Neo4j）。

## 9. 决策建议

**推荐的执行顺序与理由**：

1. **先修 P0**。当前 Agent/Workflow 路径的检索是坏的（参数名不匹配），这是**功能性缺陷**而非优化项。不修复则后续增强无法验证。
2. **再做 P1 Reranker**。零新增基础设施、3–5 人日、效果提升直接可测，是投入产出比最高的单点。
3. **P2 混合检索**紧随其后。Reranker 的价值依赖足够的粗召回候选，而纯向量召回对精确术语（编号、型号、专名）覆盖不足，混合检索是精排的前置放大器。
4. **P3/P4 图能力作为独立决策点**。建议在 P2 完成后，用评测集量化「多跳/全局类问题」占比再决定。若占比 < 15%，建议**暂缓 GraphRAG**。
5. **若确定推进图能力**，先落 MySQL 图谱表（零新增设施）跑通抽取质量，再迁 Neo4j。

**待确认的关键参数**（影响成本测算精度）：
- 实际文档总量与增长速率（决定 GraphRAG 索引成本）
- 部署形态（单机 Docker / K8s / 云托管）与可用硬件规格
- 是否有 GPU / 是否允许文档内容出网调用云 LLM
- 业务问题的类型分布（事实查询 vs 关联推理 vs 全局归纳）
- 是否愿意为检索质量投入人工标注（评测集是效果验证的前提）
