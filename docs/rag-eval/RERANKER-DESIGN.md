## 1. 问题与目标

稠密检索是**双塔（bi-encoder）**结构：查询与文档各自独立编码为向量，直到最后一步
才计算余弦相似度。这个结构带来了预计算与 ANN 检索的效率，但也意味着模型无法利用
查询与文档之间的细粒度交互，对「字面相近但语义无关」的段落容易给出高分。

**排序损失**因此成为单阶段稠密检索的主要瓶颈。Reranker 用 **CrossEncoder** 把
`(query, passage)` 拼成一个序列联合编码，直接输出相关性分数——精度更高，但无法
预计算文档向量，只能在已召回的少量候选上执行。

目标：在**不改变召回链路**的前提下补足排序能力，并让这种增强：

1. 可开关、可降级，不引入新的失败模式；
2. 关闭时与原实现**严格等价**，可在生产上灰度；
3. 与线上检索共用同一份召回实现，使评测结论可外推。

---

## 2. 架构：两段式检索

```
query
  │
  ├─► EmbeddingClient.embed()            ← 与改造前相同
  │
  ├─► search_points(limit=candidate_k)   ← 宽召回（唯一召回实现）
  │        │
  │        └─ 稠密相似度 top-K              K = candidate_k（默认 20，评测推荐 100）
  │
  ├─► MySQL 批量回表（list_by_vector_ids + joinedload）
  │
  └─► CrossEncoderReranker.rerank()      ← 新增：只对已召回候选重排
           │
           └─ 截断到 top_k → 返回
```

**关键约束：精排只能重排已召回的候选，因此 `candidate_k` 就是精排的质量上限。**
若相关分块没有被召回，精排再强也无法把它变出来。这也是评测中必须同时观察
`candidate_recall`（召回上限）与 `recall@k`（最终结果）的原因——两者之差才是
纯排序损失。

## 3. 模块设计

### 3.1 `CrossEncoderReranker`

| 能力 | 实现方式 | 理由 |
|------|----------|------|
| 懒加载 | 首次调用 `rerank()` 时才构造 `CrossEncoder` | 模型约 2 GB，未启用精排的部署不应承担冷启动开销与内存 |
| 进程级单例 | `get_reranker()` + `_reranker` 全局缓存 | `CrossEncoder` 每次实例化都会读取全部权重，请求路径上反复构造会拖垮吞吐 |
| 失败记忆 | 加载失败写入 `_load_error`，后续直接抛错 | 权重缺失/依赖不完整不会自愈，重试只会把故障成本乘以请求数 |
| 可注入 encoder | 构造参数 `encoder` | 单测不应加载 2 GB 权重；注入替身后排序契约可被独立验证 |
| 稳定排序 | `sorted(key=(-score, index))` | 同分时保持候选原顺序，保证同一输入得到同一输出 |
| NaN 兜底 | 压到 `-inf` 并记日志 | NaN 参与比较时结果未定义，会让评测不可复现 |
| 文本兜底截断 | `_MAX_TEXT_CHARS = 20000` | tokenizer 之前的内存保护（模型自身按 token 截断） |

### 3.2 排序契约

`rerank(query, [(id, text), …]) -> [(id, score), …]`

* **输入输出一一对应**：不增不删。静默丢弃候选项会让 Recall 无故下降，
  且极难排查（表现为「精排后指标变差」但无任何报错）。
* **调用方决定去重/覆盖语义**：精排层不假设业务对「同一文档多个分块」的处置方式。
* 分数是**未归一化 logit**，只有相对含义。

### 3.3 字段语义（`search()` 返回值）

| 字段 | 关闭精排 | 开启精排 | 用途 |
|------|----------|----------|------|
| `score` | 稠密相似度 | `sigmoid(精排 logit)` | 展示分数，**始终与返回顺序单调一致** |
| `retrieval_score` | 稠密相似度 | 稠密相似度（不变） | 诊断：区分「召回没捞到」与「捞到了但排太后」 |
| `rerank_score` | 不存在 | 精排原始 logit | 诊断与阈值标定 |

**为什么要把 `score` 换成 `sigmoid(logit)`**：CrossEncoder 输出可为负数且无上界。
若 `score` 保留稠密相似度而顺序按精排排列，界面上的「分数」与「顺序」会互相矛盾
（排第一的结果分数反而更低）。压缩到 `(0, 1)` 后两者单调一致，视觉语义也正常。

> 注意：`sigmoid(logit)` **不是概率**，只用于展示与相对比较。

## 4. 配置项

| 配置 | 默认 | 说明 |
|------|------|------|
| `reranker_enabled` | `False` | 默认关闭。精排引入额外延迟，且最优候选数随知识库而异，必须按库标定后再开启 |
| `reranker_model` | `BAAI/bge-reranker-v2-m3` | 中文重排效果强；本机已缓存 2.1 GB，离线可用 |
| `reranker_device` | `cpu` | `cpu` / `mps` / `cuda`。生产 Docker 为 CPU |
| `reranker_candidate_k` | `20` | 宽召回条数，直接决定质量上限与延迟 |
| `reranker_batch_size` | `32` | 推理批大小 |
| `reranker_max_length` | `512` | 输入截断长度；过长显著拖慢 CPU 推理 |

### 与现有配置的关系

- 沿用既有 `embedding_device` 的设备语义（`cpu` / `cuda`，本机扩展支持 `mps`）；
- 与 `retrieval_score_threshold` 正交：阈值作用于**召回**阶段，精排作用于**排序**
  阶段。经验上候选集交给精排裁量时，召回阶段应保持 `0.0`（不硬截断），
  否则会在精排之前就把正确答案丢掉。

## 5. 降级策略

精排是**增强**而非必需环节。任一环节失败都不得让检索整体不可用：

| 失败点 | 行为 |
|--------|------|
| `sentence-transformers` 未安装 | 抛 `RerankerUnavailable` → `search()` 捕获、记 warning、返回稠密顺序 |
| 权重缺失 / 设备不可用 | 同上，且**记忆失败**避免重复尝试 |
| 推理抛错（OOM、设备异常） | 同上，本次请求降级 |
| 返回分数个数与候选不匹配 | 抛 `RerankerUnavailable`（宁可降级，不可错位打分） |

`search()` 侧的降级点：

```python
try:
    ordered = reranker.rerank(query, [(item["id"], item["content"]) for item in chunks_data])
except RerankerUnavailable as exc:
    logger.warning("Reranker unavailable, falling back to dense order: %s", exc)
    return chunks_data
```

## 6. 资源与部署影响

| 项 | 数值 | 说明 |
|----|------|------|
| 模型体积 | 2.1 GB（fp32 safetensors） | 需进入镜像或挂载为卷 |
| 常驻内存 | 约 2.4 GB（含 tokenizer 与推理缓冲） | **仅在首次调用后占用**；未开启精排的进程不占用 |
| 依赖 | `sentence-transformers` + `torch` | **均已在 `requirements.txt` 中**，无新增依赖 |

### 6.1 延迟实测（Phase 3.4）

测量条件：`bge-reranker-v2-m3`，`max_length=512`，真实分块文本（约 1024 字符，
中文接近 1 字 ≈ 1 token，故绝大多数输入被截断到 512 token），权重已本地缓存，
测量样本 64 对（另以 128 对复核 batch 扫描）。本机为 Apple Silicon、无 CUDA，
且处于高内存压力环境（Docker VM 占 8 GB，系统压缩器占用约 5.8 GB）。

| 设备 | 加载耗时 | 精排吞吐 | 单位换算 |
|------|----------|----------|----------|
| CPU | 2.1 s | **1.59 对/秒** | 20 候选 ≈ 12.6 s/查询；100 候选 ≈ 62.9 s/查询 |
| MPS | 1.9 s | **2.69 对/秒** | 20 候选 ≈ 7.4 s/查询；100 候选 ≈ 37.2 s/查询 |

batch_size 扫描（MPS，128 对样本）：

| batch_size | 吞吐 | 结论 |
|------------|------|------|
| **32** | **2.76 对/秒** | 默认值；本机最优 |
| 64 | 2.34 对/秒 | 反而更慢 |
| 128 | 1.49 对/秒 | 显著更慢 |

> **结论**：在内存压力下，更大的 batch 会抬高激活内存峰值并加剧换页，吞吐不升反降。
> 既有默认值 `reranker_batch_size=32` 无需调整。

### 6.2 对部署的直接含义

**精排在本机硬件上不具备交互式可用性。** 即便取配置默认的 `candidate_k=20`，
MPS 单查询精排也要约 7.4 秒、CPU 约 12.6 秒；若按评测推荐把 `candidate_k` 提到
100，则升至 37～63 秒/查询。

这不是「调参能解决」的问题：568M 参数的 CrossEncoder 在 `max_length=512` 下的
计算量是刚性的（单批 32 对约 1.9e13 FLOPs），CPU 与 MPS 都只能提供个位数
TFLOPS 的有效算力。因此：

1. `reranker_enabled` 默认 `False` 是正确决策，**不得在同步请求路径上默认开启**；
2. 若确需开启，应限定为高价值场景（如「深度检索」显式触发）或异步/离线批处理；
3. 需要交互式精排时必须引入 CUDA，或改用参数量更小的重排模型
   （如 `bge-reranker-base`）并下调 `max_length`；
4. 调大 `candidate_k` 前必须先用质量–延迟曲线论证收益（见 Phase 4.3 结论）。

### 待办（不属于本批次）

1. **镜像交付**：`Dockerfile` 需在构建期预下载 `bge-reranker-v2-m3`，否则首次请求
   会触发联网下载（内网环境直接失败）。属于部署项，纳入批次 3 的文档与验证清单。
2. **GPU 部署**：`cpu` 版 torch 无法使用 CUDA。若需 GPU 精排，需换成 CUDA 版 torch，
   镜像体积与构建时间将显著增加。

## 7. 为什么不在评测侧另写一份精排实现

评测使用 `RerankedRetriever`（`app/rag_eval/retrievers.py`）而非直接调用
`search()`，但**精排函数是同一个对象**（`get_reranker().rerank`）。
评测侧的装饰器只负责编排（宽召回 → 精排 → 候选折叠），不重复实现打分逻辑。

同理，召回侧 `QdrantRetriever` 与业务 `search()` 共用 `core/vector_db.search_points`。
**任一侧单独改动都会导致评测口径与线上口径分叉**，届时评测结论将不再适用于线上——
这是评测体系最容易失效的地方。

## 8. 测试策略

| 层次 | 手段 | 覆盖 |
|------|------|------|
| 排序契约 | 注入 `FakeEncoder` | 降序、同分稳定、一一对应、NaN 兜底、预处理截断 |
| 失败降级 | monkeypatch `CrossEncoder` 抛错 | 抛 `RerankerUnavailable`、失败记忆、`warmup` 提前暴露 |
| 集成 | stub repo + 替换 `search_points` | 关闭时等价、宽召回、顺序与分数单调、降级回落 |
| 真实模型 | 评测集（Phase 4） | 质量增益与延迟——单测不回答这两个问题 |

**单测不加载真实权重**：模型 2 GB，会让测试从秒级变成分钟级并依赖网络与磁盘缓存。

## 9. 已知限制

1. **延迟与候选数线性相关，且绝对值很高**：实测 MPS 2.69 对/秒、CPU 1.59 对/秒，
   `candidate_k` 从 20 提到 100 会使精排耗时增至约 5 倍（7.4 s → 37.2 s/查询，MPS）。
   详见 §6.1 / §6.2。**默认值 20 在本评测语料上只留下约 0.5pp 的召回上限余量**
   （见下一条），是一个偏保守的取值。
2. **`candidate_k` 默认值偏小**：评测实测段落级召回上限为
   `k=10: 0.8900 / k=20: 0.8950 / k=50: 0.9050 / k=100: 0.9600 / k=200: 0.9600`。
   曲线在 `k=100` 后进入平台。`k=20` 的上限（0.8950）仅比纯稠密 `recall@10`
   （0.8900）高 0.5pp，意味着按默认值开启精排几乎不可能带来可观测的收益——
   **这不是精排无效，而是候选集没给它留出空间**。生产上若要启用精排，应先把
   `candidate_k` 提到 100，并接受相应的延迟代价（或先解决延迟问题）。
3. **无法修复召回损失**：相关分块未被召回时，精排无能为力。若评测显示
   `candidate_recall` 已是瓶颈，应优先投入混合检索（Phase 5）而非继续加大
   `candidate_k`。
4. **长文档被截断**：`max_length=512` 会截断超长分块。当前分块上限为 1024 字符，
   中文约 1 字 ≈ 1 token，故部分分块会被截断；这是延迟与精度的显式取舍，
   调高 `reranker_max_length` 可改善但会显著增加 CPU 耗时。
5. **单例不可热更**：模型切换需重启进程（配置变更后调用 `reset_reranker_cache()`）。
